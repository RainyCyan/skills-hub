# 方案评审闭环

从主 `SKILL.md` 的 Step 0 分流到此：评审对象是一个**已成形但尚未实现**的方案（落盘的设计文档 / RFC / ADR / plan.md，或同一对话中已给出的具体方案输出）。

只读评审。不改方案文档，不替用户做方案决策，除非用户单独要求。方案尚未成形、意图未定时不适用本文件，改用 `grill`。

## 1. 冻结评审快照

评审对象可能漂移，先固化一个稳定锚点，之后所有 finding 挂到这个锚点上：

- 落盘方案：以文件与章节/行号为锚点，直接引用 `path:line` 或 `§章节`。
- 对话内未落盘方案：就地 restate 成 5–8 行快照（Outcome / 关键机制 / 关键前提 / 影响面），让用户确认"我评审的就是这个版本"，再逐条挂 finding。
- 抽取方案必须满足的**决策、目标与约束**：成功标准、边界、成本/期限、仓库约定、非目标。目标或约束缺失不是"通过"，而是 `信息不足`。

Never 在没有稳定锚点的情况下报 finding，也 never 把 finding 位置写成模糊自然语言。

## 2. 对齐前提（等价于代码路径的动态验证）

方案评审最常见的失败是只做"内部自洽性检查"（读文档判断逻辑通不通），而不核方案对现状的事实声明。此步是把方案评审从"读后感"变成"证据门"的关键，不可跳过：

- 阅读方案引用的真实代码、接口、schema、配置、系统现状。
- 逐条核对方案对"现状"的关键事实声明：它声称存在的函数/接口/数据/行为是否真的存在且如它所述。
- 只在证据可达时下判断。无法核实的关键前提进入"信息缺口"，never 当作已成立。
- Treat claims about the current system as unverified until code, tests, schemas, configuration, or runtime evidence supports them。

## 3. 按严重度评审

按此顺序排优先级：

1. **问题有效性**：方案是否在解真正的目标问题，还是 XY 问题 / 伪需求 / 解错了问题。
2. **前提正确性**：方案对现状的关键事实声明为假，或未经核实即被当作前提。
3. **机制可行性**：所选机制能否真正达成目标；失败路径、重试、并发、数据一致性、迁移与回滚是否成立。
4. **更优替代与长期成本**：是否忽略了长期积分代价更低、结构更简单的路径；是否过度设计（新增 ≥2 个抽象/文件但问题不足以支撑）。
5. **可逆性与影响面**：单向门、公开契约兼容性、爆炸半径、对现有系统的耦合。
6. **约束契合**：违反已声明的硬约束、成功标准或仓库约定（含 `AGENTS.md`）。
7. **完整性**：阻塞执行的未决点——接口定义、责任归属、上线/回滚策略、可观测性、测试策略缺失。

Finding 仅在四要素齐备时报告：

- 精确锚点（快照中的 `path:line` / `§章节` / restate 行）；
- 触发它的假设、输入或执行路径；
- 被违反的目标、约束或不变量；
- 若照此实施的具体后果（返工、线上故障、数据损坏、越权、不可回滚等）。

Read enough real code to prove reachability。不报风格偏好、通用最佳实践、无因果路径的思辨性风险。关键疑虑无法从可得证据解决时，列入"信息缺口"，不要转成 finding。

## 4. 判定

用且仅用一个判定：

- `需要修改`：存在至少一个阻塞缺陷——解错问题、关键前提为假、机制不成立、忽略了明显更优且更简单的方案、违反硬约束、或存在阻塞执行的未决点。
- `信息不足`：无阻塞缺陷被证明，但目标、约束或关键前提无法核实。
- `可以推进`：无阻塞缺陷，关键前提已核实，替代方案已权衡。判定含义是"未发现阻塞缺陷"，**不是**"方案正确"——只读评审无法背书正确性，不要越界给确定性结论。
- `无方案`：范围内无可评审的具体方案。

分类：

- **阻塞**：解错问题、关键前提为假、机制无法达成目标、忽略明显更优方案、违反硬约束、或未决点会挡住执行。
- **警告**：已证明的非阻塞风险或长期成本（需特定条件才触发的机制缺口、非默认配置下的可行性风险）。
- **建议**：默认省略；仅当用户明确要改进建议时给出。

## 有界评审与升级

摘自 planloop 的唯一硬规则：方案评审不无限迭代。

- 若同一方案连续修订后仍反复产生**阻塞**级 finding，不要再进下一轮挑错。
- 显式升级：说明"方案已修订 N 轮仍持续生成阻塞项，问题可能出在 spec 或范围本身，建议退回 `grill` 重新确认意图或重写方案，而非继续评审"，然后停。

## 输出契约

沿用主 `SKILL.md` 的输出结构，替换两处：判定词用本文件第 4 节的四选一；"动态验证"小节替换为"前提核对"。

```markdown
## 审查结论

**判定**: 需要修改 | 信息不足 | 可以推进 | 无方案
**范围**: [评审的方案锚点——文件/章节，或对话内快照标识]

### 阻塞项
- `§章节 / path:line / 快照行` — [问题]
  - 触发假设: [假设/输入/执行路径]
  - 影响: [具体后果]

### 警告项
- `§章节 / path:line` — [问题与后果]

### 前提核对
- [方案对现状的关键声明] — 已核实(证据) | 为假(证据) | 无法核实

### 信息缺口
- [缺失的证据及其为何影响置信度]
```

无 finding 时说明 `未发现阻塞缺陷`；never 用"方案正确"之类的背书替换这句话。除非用户要求，remediation 不进报告。
