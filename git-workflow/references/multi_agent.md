如何并行运行3到8个编码代理而不失去跟踪
同时启动多个Claude Code或Codex代理很简单。保持控制是问题所在。这里是实际有效的方法。

2026年6月1日
同时运行两个代理只需要五分钟。你打开两个终端，给每个分配一个任务，然后看着文本滚动。

问题从第四个开始。

你不再知道哪个在等待审核，哪个已经完成，哪个在你看向别处时十分钟前崩溃了。你在错误的终端滚动。你重新启动了一个已经完成的任务。一个小时后，你为了保持方向感而手动完成了三个代理的工作。

这不是一个计算能力的问题。这是一个可见性的问题。

真正的瓶颈在于你的头脑
一个自主编码的代理是间歇性地交付。它思考40秒，写作，停止，等待你的批准。在这40秒内，你可以跟随第二个代理。当第二个代理写作时，你批准第一个。

最多3个代理，你的大脑还能跟上。超过5个，你就掉线了。

Anthropic在其文档中发布了一个有说服力的数字：无指导的尝试大约三分之一会成功。那些能够大量交付的人与其他人的差距不在于模型，而在于他们在启动之前所建立的结构。

所以在你扩展之前，你需要建立结构。

规则一：一个代理，一个独立的工作空间
经典的错误是将三个代理放在同一个代码库的副本上。它们互相干扰。一个编辑了package.json，另一个也编辑了，结果你得到一个无法解开的合并。

解决方法是两个词：git worktree。

git worktree add ../project-auth feature/auth
git worktree add ../project-billing feature/billing
git worktree add ../project-export feature/export
每个代理在自己的文件夹中工作，在自己的分支上，使用自己的文件。零冲突。你分别审核每个分支，并在准备好时合并。

这是研究人员称之为独立委派的基础：一个中央管理者分配工作，每个子任务在自己的角落运行，集成在之后进行，并通过测试验证。

规则二：永远不要两次分配相同的中央文件
在你分配工作之前，找出多个功能需要触及的文件。路由器，数据库模式，API路由配置。

这些文件只分配给一个代理。其他的等待或绕过它们。

将相同的routes.ts交给两个并行代理，你将在合并冲突中付出你以为可以通过并行获得的代价。这个交易每次都会失败。

规则三：一个面板，而不是十个终端
这是大多数人放弃多代理的地方。他们打开八个终端标签，失去线索，然后爬回到单个代理。

你需要一个视图，可以一目了然地回答三个问题：

谁正在编码？
谁在等待我的审核？
谁完成了或崩溃了？
没有这个视图，多代理在心理负担上花费的比它在速度上给予的更多。有了它，你可以真正同时处理6到8个工作流。

这正是AgentsRoom填补的空白。每个代理都有自己的方块、状态和颜色。等待你回复的代理会变红并提醒你。你不再滚动错误的终端，你看着面板就知道该去哪里。

实践中有效的节奏
这是我会开始的节奏。

从两个代理开始，处理两个不共享文件的功能。习惯审核然后合并的循环。这个循环，而不是代码，成为你的真正工作。

一旦这个循环感觉顺畅，增加到四个。保持一个严格的高影响任务优先级列表，并在计划模式上努力：你在代理写一行代码之前批准它的计划。事先批准的计划可以为你节省痛苦的审核。

最佳点在于同一个代码库上的3到8个功能，并有视觉监督。超过这个，即使有一个好的面板，审核也会成为瓶颈，你会失去优势。

你实际获得的是什么
对于95%的小任务，多代理是没有意义的。修复一个错字或添加一个按钮，一个代理就足够了，而且更快。

它改变你一周的地方在于大工作。你在一个晚上启动三个独立的重构，在它们到达时审核，第二天早上你就有三天的工作准备合并。

秘密不在于代理的数量。关键在于始终知道哪个代理现在需要你。解决这个问题，其他的就会随之而来。
