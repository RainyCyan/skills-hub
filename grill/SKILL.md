# Grill

在实现开始前把"要求"和"真实意图"的缺口关掉。最便宜的时刻是任何 plan/spec/code 存在之前——一旦开工，切换成本变高，用户会把错的东西合理化成"够用"，错配就被锁死。

## HARD GATE

Never 写代码、写 spec、写 plan、scaffold 工程或调用任何实现类 skill，直到你已 restate 意图且用户给出**显式 yes**。此门对每个任务生效，无论看起来多简单——"太简单不值得澄清"正是未审视假设造成最多返工的地方。

## 何时不启动

- 需求已明确且自包含（"重命名这个变量"、"修这个 typo"）。
- 用户已明确要求"速度优先、跳过确认"。
- 纯信息查询（"X 怎么工作"、"这段代码做什么"）或机械操作（重命名、格式化、移动文件）。
- 你已有 ≥95% 置信——先读下方停止条件再判断，别默认自己没有。

Only 在有一个**活跃、可响应的用户**时运行。CI、定时任务、`/loop`、自主循环里不要启动；若此时需求欠定，把它作为阻塞项抛给用户，而不是猜。

## 流程

严格按序，脆弱易错，不可跳步。

### 1. 先写假设，附一个置信数字

问任何问题之前，用**一句话**写下你此刻对用户想要什么的最佳读数，加一个诚实的置信度（0–100%）：

```
HYPOTHESIS: 你想要在站会上回答"我们进展如何"，"dashboard"只是第一个想到的惯例说法。
CONFIDENCE: ~30% — 缺：给谁看、这里的"指标"具体指什么、成功长什么样
```

数字强制诚实。若写了高分却无法预测用户对接下来三个问题的反应，这个数字就是错的。置信度低于 ~70% 时，在同一行附一句原因（还差什么），否则用户无从帮你补齐。

### 2. 一次一问，每问都附上你的猜测

格式：

```
Q: <一个聚焦的问题>
GUESS: <你对答案的假设，以及得出它的推理>
```

问完等用户反应，再问下一个。

- Never 一条消息里塞三个及以上问题——那是问卷，不是访谈。
- Never 只问不附猜测——那是调查，不是承诺。
- 一次一问的理由：用户对错的猜测反应比从零生成答案更快；第三个问题常依赖第一个的答案，一次问完会锁死错的框架；用户认真思考的精力有限。

风险是礼貌型用户为附和而同意你的猜测。对冲：明显地表现出你愿意被推翻，并偶尔故意猜一个你预期用户会反对的方向。

### 3. 听辨"想要 vs 以为该要"

最危险的答案是用户说出"一个深思熟虑的答案听起来的样子"，而非他真正想要的。警惕：

- 套最佳实践话术（"我想要可扩展"、"clean architecture"）却无具体项。
- 诉诸惯例（"大多数 app 那样"、"标准做法"）。
- "我大概应该…"、"我觉得我该…"、"好的工程实践要求…"。
- 用 buzzword 当目标（"modern"、"scalable"、"robust"）替代具体结果。

听到这些时，问这一句——它往往顶过前面五个问题：

> "如果你不用向任何人交代，你到底想要什么？"

### 4. 用用户自己的话 restate 意图

置信度高时，把你现在认为用户想要的写回去，紧凑（5–8 行），尽量用他的措辞，逐行可确认可纠正：

```
我现在理解你想要的是：

- Outcome:      <一行——要达成的结果>
- User:         <一行——谁受益>
- Why now:      <一行——什么变了>
- Success:      <一行——怎么算成功>
- Constraint:   <一行——绑定性的限制>
- Out of scope: <一行——明确不做什么>

Yes / no / refine?
```

"Out of scope" 不可省略——一半的错配来自对"不做什么"的沉默分歧。

### 5. 确认——要显式 yes，不接受"你看着办"

门槛是显式的 "yes"。以下都**不是** yes：

- "你看着办" → 用户在委托，说明他也没有 95% 把握。用两个具体选项重问。
- "听起来不错" → 含糊。追问："有什么想调整的吗？"沉默不是确认。
- "行，走吧" → 常是礼貌性收场。同样追问。
- 沉默后接"好那开始吧" → 用户是放弃了访谈，不是收敛了。停下问是不是漏了什么。

被纠正就把纠正折进去重新 restate，循环直到拿到显式 yes。

### 停止条件：95%

当你能对下面这句回答"是"，就完成了：

> 我能预测用户对我接下来会问的三个问题的反应吗？

能，就有了共识：停止访谈，产出 restate。不能，就没完成：接着问。这是可检验的测试，不是感觉。它也有下限：若已问了数轮仍无法预测，那是关于需求本身的信息，而非继续磨的理由——停下并告诉用户"我问了 X 个问题仍无法预测你的反应，有些根本性的东西缺失了，要不要退一步？"

## 输出

本 skill 的产物是一份**已确认的意图陈述**：第 4 步的 restate + 第 5 步的显式 yes。spec、plan、任务清单都是下游，消费这份意图。

若用户希望意图持久化（跨会话项目、交接给他人），offer 保存到 `docs/intent/<topic>.md`——Only if 用户确认后再存，别抢先建文件（文件本身暗示了一个用户没给的 yes）。

## 自检

结束前逐条确认，任一不满足则继续：

- 首轮是否给出了显式假设 + 置信数字？
- 每个 <70% 的置信度是否附了原因？
- 是否一次一问、每问附猜测？
- 用户给出 buzzword/惯例型答案时，是否至少问过一次"不用交代的话你到底想要什么"？
- restate 是否含 Outcome / User / Why now / Success / Constraint / Out of scope 六项？
- 是否拿到显式 yes（非"你看着办"、非"听起来不错"、非沉默）？
- 停止点上，你能否预测接下来三个问题的反应？
